## B. Audit retention and backup decisions

### Audit retention options

| Option | Benefits | Costs / risks |
|---|---|---|
| 1 year searchable | Lower storage and exposure window; simpler subject deletion. | Short incident investigation and business dispute lookback; may conflict with applicable obligations. |
| **3 years searchable (recommended proposal)** | Practical security/governance investigation window without defaulting to indefinite retention. | Still requires lawful-purpose review, data minimization, controlled purge and backup expiry alignment. |
| 7 years or longer / archive | Better long-range investigation and potential regulated record needs. | Higher exposure and storage burden; likely unnecessary absent a legal/business requirement; increases erasure complexity. |

Recommended default for owner decision: keep minimized audit events queryable for 3 years, then purge or irreversibly aggregate unless a documented legal hold applies. This is a proposal, not a legal determination. Separate event classes (security/role changes, operational activity, public lead changes) only if retention needs differ. Append-only DB permissions prevent application-level edits/deletes, but do not make rows immutable against database owners; tamper-evident off-database archival would require a separately approved destination and key/access controls.

### Development backup and restore options

| Option | Database | Storage object bytes | Trade-offs |
|---|---|---|---|
| Managed Supabase backup/PITR | If the actual plan and project configuration provide it, use the displayed daily-backup retention or separately priced PITR. Confirm current coverage, cadence, retention, and restore downtime in the project dashboard before relying on it. | Not included in database backups; separately inventory/export object bytes. | Lowest operator burden, but capability/price/retention are subscription-dependent; restore is project-wide and may cause downtime. |
| Encrypted logical export to owner-approved private object storage | Scheduled `supabase db dump`/PostgreSQL logical dump with separately protected schema, data, and role material as applicable. CLI dumps exclude Supabase-managed `auth` and `storage` schemas by default; customizations there need migration/source capture and Auth data requires an explicitly approved treatment. | Export/copy the object bytes separately using an approved Storage export procedure; retain object keys/checksums and verify metadata-to-object reconciliation. | Portable and independent of provider backup tier; needs scheduled automation, encryption/key custody, restricted access, and storage cost. Never place dumps in the repository or public CI artifacts. |
| Migration-only reconstruction | Versioned DDL recreates schema and policies; synthetic seed only. | Re-upload approved test files, if any. | Good for clean dev reset, not a backup of mutable database content or uploaded files. |

Recommended development default for owner decision: use provider backups only after verifying eligibility and actual retention, plus an encrypted owner-selected logical export before every remote schema migration and nightly while the environment contains irreplaceable test/business data; separately export Storage bytes on the same cadence. Proposed retention: 30 daily points, with one monthly point for 6 months only if the owner-selected destination supports it and cost/privacy review approves. Keep no database dumps in Git. Restore into an isolated non-production target, never over the source during a test. Reconcile schema/migration history, row counts, RLS/grants, bucket/object counts and checksums; record completion and elapsed time.

Recovery targets must be selected by the owner. Suggested development targets for approval: RPO 24 hours and RTO 1 business day for scheduled exports (with pre-migration snapshots reducing migration-specific loss); managed PITR can offer a tighter database RPO only if subscribed/configured, but does not restore Storage object bytes. Record tested database and Storage RPO/RTO separately. Supabase states managed daily backups are plan-dependent, PITR is an add-on, and database backups omit Storage API object bytes; CLI dumps exclude managed schemas by default. See [Supabase backup coverage](https://supabase.com/docs/guides/platform/backups), [CLI database dump](https://supabase.com/docs/reference/cli/supabase-db-dump), [Storage object download](https://supabase.com/docs/guides/storage/management/download-objects), and [database migrations](https://supabase.com/docs/guides/deployment/database-migrations).

## C. Proposed core schema

UUID primary keys and `timestamptz` audit times throughout. Application tables exposed through the Data API live in `public` with RLS enabled. Authorization helpers live in a non-exposed schema. Explicit grants accompany policies; default privileges grant no table access to `anon`. Auth passwords/factors stay in Supabase-managed Auth.

### Identity, organizations, and roles

- **`profiles`**: `id uuid PRIMARY KEY REFERENCES auth.users(id) ON DELETE RESTRICT`; minimal profile fields only; `created_at`, `updated_at`. Create/update via trusted Auth lifecycle workflow; user may read/update only an explicitly permitted subset of their own profile fields. Never use user-editable Auth metadata for authorization.
- **`organizations`**: `id uuid PK DEFAULT gen_random_uuid()`, `name text NOT NULL`, `status text NOT NULL CHECK IN ('active','suspended','deleted')`, `created_at`, `updated_at`, nullable `deleted_at`, and nullable `created_by` FK to profile with `ON DELETE RESTRICT`. Name is not globally unique. Deleted organizations cannot be reactivated implicitly; restore requires explicit authorized audited action.
- **`organization_memberships`**: PK `(organization_id,user_id)`; both FKs `ON DELETE RESTRICT`; `status` in `active/suspended/removed`; timestamps and `created_by`. A suspended/deleted organization or non-active membership denies all tenant access. Invitation lifecycle is separate and not created here.
- **`organization_role_assignments`**: UUID `id PK`; `(organization_id,user_id)` FK to membership `ON DELETE RESTRICT`; role CHECK in `organization_owner/organization_admin/project_manager/client_member`; `assigned_by` FK to profile; `assigned_at`, nullable `revoked_at`, optional reason code. Partial unique index on `(organization_id,user_id) WHERE revoked_at IS NULL` permits one current base role per membership while retaining history. Membership activation and its role assignment are one transaction; a deferred integrity check/controlled transaction must prevent committing an active membership without exactly one current role. Reassignment revokes old and inserts new role atomically. No automatic Owner-count invariant is added.
- **`platform_role_assignments`**: UUID `id PK`; `user_id` FK profile `ON DELETE RESTRICT`; role CHECK in `platform_admin/developer/support_staff`; status `active/revoked`, `assigned_by`, `assigned_at`, nullable `revoked_at`. Partial unique index `(user_id,role) WHERE status='active'`. The Super Admin role does not live in this table. Platform assignment requires explicit authorized server operation and MFA verification.
- **`platform_super_admin_designation`**: singleton `slot smallint PRIMARY KEY CHECK (slot=1)`, `user_id uuid NOT NULL UNIQUE REFERENCES profiles(id) ON DELETE RESTRICT`, `designated_at`, `designated_by` FK and transfer metadata. Migration creates the empty table only. At most one row is structural; exactly one active designation is an operational invariant after separately authorized bootstrap. All protected platform operations fail closed while empty. Once initialized, only a serialized, authorized transfer transaction may replace the user and must write its audit event atomically. Prevent ordinary role/session/account deletion paths from disabling or removing the current designee. No migration seeds a row or user.

### Audit and CRM boundary

- **`audit_events`**: UUID id, `occurred_at timestamptz NOT NULL`, nullable `actor_user_id` FK with `ON DELETE SET NULL` (preserve event on identity erasure), nullable `organization_id` FK `ON DELETE RESTRICT`, `scope` check (`platform`/`organization`), event/action code, target type and UUID/text identifier, request/correlation id, minimized `jsonb` details, and optional retention/hold metadata. Check that platform events have no tenant scope unless explicitly designed; organization events require `organization_id`. No credentials, tokens, full request bodies, or unnecessary personal data. Application roles receive insert-only via narrowly scoped audited server operation; no direct client write, update, or delete. Read access limited to authorized governance/support scope and MFA assurance.
- **`platform_sales_leads`** (follow-up CRM migration, owner decision approved): platform-owned public leads have no `organization_id`; separate platform authorization and spam/rate-limit controls. Do not expose as tenant-owned leads.
- **Tenant CRM** (later tenant-feature migration): every client-org record carries `organization_id`; composite unique/FKs `(organization_id,id)` ensure contacts/companies/activities cannot link across organizations. Define specific entities after workflow requirements; CRM never reads/writes `platform_sales_leads` through shared policy paths.

### Constraints, indexes, and grants

- Index every FK lookup and RLS predicate: memberships `(user_id,status,organization_id)` and `(organization_id,status,user_id)`; current role lookups `(user_id,organization_id)` with the active partial predicate; active platform assignments `(user_id,role)`; organizations `(status,created_at DESC)`; audit `(occurred_at DESC)`, `(organization_id,occurred_at DESC)`, `(actor_user_id,occurred_at DESC)`; designation unique user key. Add feature indexes only from measured query patterns.
- No `ON DELETE CASCADE` through organizations, memberships, assignments, audit, or tenant business records. Use suspension/soft deletion; physical deletion requires approved retention/erasure workflow. FK and status checks protect referential integrity.
- Revoke broad default table/sequence/function privileges from `anon` and `authenticated`, then grant only required operations. Policies do not substitute for SQL grants. Never grant access to RLS tables without policies. Private helper schema is not Data API exposed.
- MFA checks use `auth.jwt()->>'aal' = 'aal2'` as a restrictive condition where privileged operations are exposed to user sessions, paired with role/scope policy and server-side validation. Do not trust `user_metadata` for role decisions. Current Supabase MFA guidance documents AAL2-based RLS enforcement: [MFA policies](https://supabase.com/docs/guides/auth/auth-mfa).

### Initial table policy matrix

| Table | Intended access after explicit SQL grant |
|---|---|
| `profiles` | Authenticated user reads own profile and updates only approved non-authoritative fields. No client changes to role, status, or identity links. |
| `organizations` | Active members read their own active organization. Platform Admin with AAL2 creates/suspends/soft-deletes/restores. No member can change organization status. |
| `organization_memberships` | Member reads own membership; Organization Owner/Admin with AAL2 administer membership in that same organization, subject to server permission checks. A user's role never grants access to another organization. |
| `organization_role_assignments` | Self may read current own role; Organization Owner/Admin with AAL2 can make scoped role changes through an atomic audited operation. No self-grant/escalation. |
| `platform_role_assignments` | No direct client writes. Read scope limited to authorized platform governance. Platform Admin/Super Admin grant/revoke through a controlled audited operation, MFA required; never self-grant. |
| `platform_super_admin_designation` | No direct `anon`/`authenticated` write. Empty is readable only as a readiness state to server-side gate, not public API. Change only through the separately authorized serialized bootstrap/transfer procedure. |
| `audit_events` | No direct client writes or updates/deletes. Trusted server operations insert with actor derived from verified session; governance readers see only authorized platform or tenant scope and use AAL2. |
| `platform_sales_leads` | No public Data API access. Rate-limited server endpoint may create a lead; platform CRM roles read/update with scoped grants and server checks. Tenant roles get no access. |
| Tenant CRM tables | Active members read only rows for their organization and role scope; client member access limited to relationship/ownership. No cross-tenant reads or writes. |

Every update policy needs both `USING` and `WITH CHECK`; validate SQL grants separately because RLS cannot grant table privileges. Any privileged server path that bypasses RLS must perform equivalent role/scope/AAL2 validation and create an audit event in the same transaction where feasible.

## E. Security and RLS validation plan

For each test, use distinct synthetic users across two organizations plus platform-only roles, and run as `anon`, authenticated sessions at `aal1`/`aal2`, and narrowly authorized server operations. Test SELECT/INSERT/UPDATE/DELETE separately, including both `USING` and `WITH CHECK` behavior.

- Anonymous/public requests cannot enumerate profiles, organizations, memberships, assignments, audit, platform sales leads, or tenant CRM; no public signup path is created.
- A member sees only rows for active memberships and active organizations. Suspended/removed membership and suspended/deleted organization deny reads and writes immediately.
- Multi-org users see each explicitly joined tenant only; org role in one tenant has no effect in another.
- Attempt cross-org parent references, forged `organization_id`, row reassignment to another tenant, role escalation, assignment self-grant, and querying by guessed UUID; all denied by composite FKs/RLS/grants.
- Platform roles authorize only listed platform actions and never through organization membership. Platform sales leads are invisible to client members and org admins; tenant CRM records are invisible to other tenants and public platform-lead roles unless an explicit platform permission grants them.
- Privileged roles at `aal1` cannot access privileged data/actions; approved roles at `aal2` can only access their permitted scopes. Missing/stale/unverified role claims fail closed; role changes are read from authoritative DB state.
- Audit insertion captures actor/scope/action/target, strips secrets, and is available only to scoped authorized readers; clients cannot update/delete or forge actor identity. Test user erasure preserves audit event while removing identifying FK.
- Empty Super Admin slot blocks protected platform use. No role grants or ordinary update/delete can populate/remove/change the slot. Concurrent attempted transfer, demotion, deactivation, deletion, and audit failure must preserve one active designation at commit or roll back as a unit. Bootstrap is not part of these migrations.
- Verify grants independently of RLS, function execute privileges, helper schema exposure, Storage object authorization, and generated API surface. Supabase documents RLS and policy test workflows in [Postgres RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).
